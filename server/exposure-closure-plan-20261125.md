## 二、总原则与批次总览

原则（每批都守）：
1. **先验新通道、再关旧面**：任何收口动作之前，先把替代访问路径（SSH 隧道回环）实测打通并留证，再动公网面。
2. **不并批动两个登录面**：SSH 与宝塔不同批同时收，永远留一个带外兜底面活着。
3. **每批独立备份、独立验收、独立可回滚**；上一批验收不过，不进下一批。
4. 施工挑低峰：避开整点后 5 分的评估轮与 07:30/08:30 生成轮；容器重建的秒级中断选无在飞任务时段。
5. 施工前后各查一次内存，>80% 停手。

## 三、H1 — mihomo 控制面（9097 面板 / 9098 控制器）绑回环

**现状**：metacubexd 容器映射 0.0.0.0:9097→8080（Web 面板）、0.0.0.0:9098→9090（控制器 API），容器内 active.yaml 为 external-controller=0.0.0.0:9090、allow-lan=true。公网任何人可达，只靠 48 字符 secret 挡爆破。

**主案（推荐）：docker 映射改绑回环**
1. 备份 /opt/metacubexd/compose.yaml 到回滚目录（见第六节），并存 `docker inspect metacubexd` 与 `ss -tlnp` 快照。
2. 先验替代通道：用既有密钥通道起隧道（`ssh -L 9097:127.0.0.1:9097 -L 9098:127.0.0.1:9098` 走现行 bt3128 同路），确认隧道下能打开面板——注意此时公网映射还在，隧道命中的是同一个服务，验的是「回环路径通」这一事实本身。
3. 改 compose.yaml 两行端口为 `127.0.0.1:9097:8080`、`127.0.0.1:9098:9090`（与同文件 7890 的现行写法一致）；active.yaml 的 external-controller/allow-lan **不动**（容器内回环外仍需监听容器网卡，收口点在 docker 映射层，改动面最小）。
4. `docker compose up -d` 重建容器（秒级代理中断；7890 消费者为本机进程，重建后自动恢复，restart=unless-stopped）。
5. 验收：本机 `ss` 确认 9097/9098 只剩 127.0.0.1 且无 `[::]` 残留；隧道打开面板＋控制器 API 带 secret 实测可用；经 7890 代理出网实测通；再走第五节公网复测。

**备选（不推荐）**：云安全组给 9097/9098 加来源白名单。缺点：家庭宽带 IP 动态、外出即失效，且要动控制台；仅当用户明确要保留公网直达面板时才选。

**影响**：用户本人从浏览器公网直开 metacubexd 面板的习惯改走隧道（Mac 上一条命令）；服务器本机进程用 7890 代理不受影响；Hermes 等业务零影响。

**回滚**：还原 compose.yaml 备份 → `docker compose up -d` → 公网复测两端口恢复 OPEN 即回滚完成。预计 1 分钟内。

## 四、M4 — allinssl 证书管理面（7979）绑回环

**同批理由**：与 H1 同技术动作（改 compose 端口映射绑回环）、同复测方法、同样不碰任何登录通道，两件合批只多一次容器重建；且 allinssl 是低频使用的证书管理面，公网敞着的每一天都是纯风险敞口，没必要单独再等一批。

**改法**（与 H1 同序）：备份 /www/dk_project/dk_app/allinssl/allinssl_BYR8/docker-compose.yml → 验隧道回环通道 → 端口改 `127.0.0.1:7979:8888` → compose up -d 重建 → 本机 ss＋隧道打开管理页实测 → 公网复测。

**影响**：证书续期是容器内部行为，不依赖 7979 公网入站，收口不影响续期；管理页改走隧道打开。

**注记（宝塔应用覆盖风险）**：allinssl 是宝塔 docker 应用，将来在宝塔里对该应用做更新/重装可能把 compose 写回 0.0.0.0。验收清单里加一条长期项：**宝塔里动过 allinssl 应用后，复查 7979 绑定**；同理适用于体检 L5 的同类提醒。

**回滚**：还原该 compose 备份 → up -d → 公网复测 7979 恢复 OPEN。


## 五、M2 — 宝塔面板（16630）去公网放行

**现状**：BT-Panel 监听 *:16630、公网实测 OPEN；安全入口已设（聊胜于无的一层），口令强度未验。面板是爆破最高价值目标，也是 M1 批次的带外兜底面之一，所以排在 SSH 之前单独成批、本批绝不动 SSH。

**主案（推荐）：云安全组删除 16630 的公网放行，访问改走 SSH 隧道**
1. 施工前留证：腾讯云控制台安全组规则现状截图/导出存回滚目录（机内看不见安全组本体，这份留证只能在控制台侧做）。
2. 先验替代通道：既有密钥通道起隧道 `ssh -L 16630:127.0.0.1:16630`，实测能打开面板并登录（面板监听 * 含回环，隧道天然可用）。
3. 控制台侧删除/禁用 16630 的入站放行规则（用户操作）。
4. 验收：公网复测 16630 为 closed/filtered；隧道访问面板照常；宝塔托管的站点（80/443）公网不受影响，逐个抽测在册站点 200。

**不采的改法**：面板内置「授权 IP」限制不作主案——经隧道访问时面板看到的来源是 127.0.0.1，面板级白名单若不含回环会把隧道路径一起锁掉，与「改走隧道」的保留通道设计冲突。如用户坚持加面板级限制，必须把 127.0.0.1 一并列入，且在 M1 批次前复验隧道＋面板双通。

**备选（弱收口，不推荐单用）**：保留公网放行，仅复核安全入口＋强口令＋面板更新。爆破面仍在，只适合作为用户暂不动安全组时的过渡。

**影响**：用户与助手从浏览器公网直开面板的习惯改走隧道；宝塔的站点/数据库/文件管理功能本身不受影响；**M1 批次施工期间，宝塔 Web 终端仍可经隧道使用，兜底链完整**。

**回滚**：控制台恢复 16630 放行规则（按留证截图原样加回）→ 公网复测恢复 OPEN。分钟级。

## 六、M1 — SSH：fail2ban 上线 ＋ 关密码登录（压轴批，防自锁顺序写死）

**现状**：22 公网开放、PasswordAuthentication yes、无 fail2ban；但全期密码成功登录 0 次、合法登录 100% 走密钥，爆破流量 1147 次失败记录。关密码的实际风险不在「有没有人用密码」（没人用），而在施工动作本身把密钥通道误伤——故本批全部笔墨在防自锁。

### 步骤 A：fail2ban 先行（独立子步，先做、可单独回滚）
1. CentOS 7 走 EPEL 归档源装 fail2ban；jail.local 只启 sshd jail（backend=systemd 或 logpath=/var/log/secure，bantime 起步 1h、maxretry 5、findtime 10m），ignoreip 含回环与我方常用出口。
2. `fail2ban-client status sshd` 实测在跑；用一次受控的错误密码尝试（从隧道外路径）验证 ban 动作真实生效，验完手动 unban。
3. 观察至少 24 小时（ban 名单应能抓到现行爆破 IP），无误伤再进步骤 B。此步不改 sshd 任何配置，零自锁风险；回滚＝停服务＋卸 jail 配置。

### 步骤 B：关密码登录（防自锁顺序，一步不许跳）
前置硬条件（全满足才动）：步骤 A 已观察满 24h；批次二（宝塔）已收完且隧道＋面板兜底实测可用；腾讯云控制台账号用户本人可登录（VNC 救援通道在用户手里）。

1. **备份**：/etc/ssh/sshd_config 复制进回滚目录，并存一份 `sshd -T` 有效配置全文快照。
2. **预置自动回滚定时器**（硬兜底）：施工第一动作先挂一个 30 分钟后自动执行的回滚任务（systemd-run/at：到期自动把 sshd_config 还原为备份并 reload sshd）。后续确认无误后手动取消；**若施工中途任何原因失联，什么都不用做，30 分钟后密码登录自动恢复原状**。
3. **保持现有会话不关**：全程在已建立的密钥会话里操作，该会话从头到尾不退出。
4. 改 sshd_config：`PasswordAuthentication no`（只改这一行；PermitRootLogin 本批不动，维持 yes＋密钥，避免一次动两个变量）。`sshd -t` 校验通过才继续，不过即还原备份收工。
5. **只 reload 不 restart**：`systemctl reload sshd`（reload 不断已建立会话）。
6. **新开第二条通道实测**：另起一条全新的 bt3128 密钥会话登录，实测成功且能执行命令；再用「只许密码、不许公钥」的客户端参数试登一次，必须被拒（证明密码面真的关了）。
7. 两项实测都过 → 取消自动回滚定时器 → 最后才关第 3 步的原会话。
8. 验收：公网复测 22 仍 OPEN（预期保留）但密码登录被拒、密钥登录正常；`sshd -T` 回读 PasswordAuthentication no 落盘；24h 后复查 /var/log/secure，Failed password 应大幅收敛（fail2ban＋无密码面双作用）。

**兜底链（按优先级）**：①自动回滚定时器（无人值守自恢复）→ ②宝塔 Web 终端（经隧道，批次二已保证可用）→ ③腾讯云控制台 VNC/救援登录（用户侧）。三层任一可用即不构成失联事故。

**影响**：对全部现行合法通道零影响（实证见第一节）；用户若在别处存有「密码登服务器」的旧习惯/脚本，施工前请先自查，关后密码方式一律失效。

**回滚**：还原 sshd_config 备份 → `sshd -t` → reload → 密码试登恢复即回滚完成；或什么都不做等定时器（仅施工窗口内）。
