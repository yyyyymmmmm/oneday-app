## 2. cron 侧实查（缺口已实际发生、且无人知晓）

- 事实源齐备：`/opt/data/cron/executions.db` 有 executions 表 54 行，其中 **status='failed' 6 行**；另有 cron_incidents 表 5 行（按 error_sig 聚合的事故账，state 全为 detected）。
- **事故从未发出**：5 行 incidents 的 `alerted_at` **全部为 NULL**、acked_at 亦全 NULL——Hermes 自家事故告警从未送达任何地方。代码侧 grep：cron_incidents 的引用只在 `cron/` 自家模块与 Dashboard 的 web_routers/cron.py，executions.db 的读者只有 cron 路由/备份/清理——**没有任何通知流消费者**。
- 最近实证（与主线已知事故逐一对上）：job「OneDay 记忆日结」2026-11-24 23:40 failed（HTTP 403 额度不足）、「OneDay 目标进展日结提炼」23:50 failed（同因）；更早 11-15 有三条脚本类 job 失败（exit code 1）。这些失败用户全靠主线人工巡检才知道，通知流里一条没有。
- 在册 cron job 共 9 个（jobs.json 实读）：OneDay 系统轮×6（点子日轮/目标周报/动态调研 A/B/动态小时评估/点子到期清理）＋记忆日结/记忆周体检/目标进展日结。

## 3. kanban 侧实查（潜伏缺口）

- 唯一看板 `oneday`：`/opt/data/kanban/boards/oneday/kanban.db`（在役、今日仍在写）。tasks 表 6 行全 done；task_runs 7 行（6 done＋1 review）。
- 失败留痕字段齐备但从未触发：tasks 有 consecutive_failures（全 0）、last_failure_error（全 NULL）、max_retries；task_runs 有 status/outcome/error；task_events 65 行的 kind 分布里**没有任何失败类事件**（claimed/completed/created/heartbeat/spawned/worker_result 等）。
- Hermes 自家 kanban 订阅表 kanban_notify_subs 为 0 行（未启用，且其投递面是聊天平台、非 OneDay 通知流）。
- 结论：kanban 失败至今未发生过，但一旦发生（worker 崩溃/重试耗尽），与 cron 同命——落进 kanban.db 后无人搬运进通知流。

## 4. 方案范围：补两个读时聚合源

沿 1.7.0 既定形态（B-03 读时聚合、不落副本、基线防回灌），给 overview_gateway.py 增两源，与现四源并列：

1. **cron 失败源**：只读打开 executions.db，按 **cron_incidents 聚合**产条目（一事故一条，first_seen 起、last_seen 更新），不按 executions 逐条产（防同一故障每轮刷屏——23:40/23:50 两条同因失败即实证）。kind 拟 `cron_failed`（含 fail 信号，App 现行分类器按 CAPABILITIES #16 口径认 kind 内 fail 归失败类，无需 App 改动）。条目内容只含生命周期事实：job 名＋失败时间＋截断清洗后的一行原因（executions.error 含 stderr 全文，**必须截断去敏、不带输出正文**，沿 runs 投影「内容绝不外泄」纪律）。基线键 `cron_since` 防历史回灌（上线前的 5 起存量事故不补发）。
2. **kanban 失败源**：只读扫描 boards/*/kanban.db 的 task_runs（status/outcome 失败态或 error 非空）产条目，kind 拟 `kanban_failed`。条目只含：任务标题＋看板名＋失败时间＋一行 error 摘要（同去敏纪律）。基线键 `kanban_since` 同理。
3. **生未读**：两源条目 born unread（与 pending 同形态，失败须打断），计入 /overview 未读数（与 pending 的不计口径相区别——待批是等待、失败是事故；此点为方案拟定，施工时如与既有口径冲突以本文件为准并回写 CAPABILITIES）。

**不在本包范围**：不动 cron/kanban 引擎本体；不启用 kanban_notify_subs；不修 Hermes 自家 incidents 告警投递（那是上游面，本包只补 OneDay 通知流）；不做 App 改动。

**备选已否决**：生产者侧把失败写进监测账本（monitor-notifications）——与读时聚合的房规相悖、且监测账本是 oneday 语义账，混入引擎失败会污染监测面。否决理由在此登记，施工不许翻案。

## 8. 验证法（施工后验收口径，先行成文）

1. **cron 活验**：建一次性测试 job（脚本 exit 1），到点执行后回读 GET /notifications——须见一条 cron_failed 未读条目（job 名＋一行原因、无 stderr 全文）；连跑两轮同因失败仍只一条（事故聚合）；验毕删测试 job，条目随源下线口径处理。
2. **kanban 活验**：新建一次性测试看板＋任务，以必失败的 worker 配置（如无效 model_override）触发 task_run 失败，回读通知流见 kanban_failed 条目；验毕整板删除。注：worker 失败的可靠触发姿势施工时先在测试看板上试定，再写进验收记录（本方案未实测该触发路径，**此点标未查实**）。
3. **基线验**：应用后首读通知流，存量 5 起 cron 事故与历史 run 不得回灌。
4. **回归验**：现四源条目形状/未读数与应用前基线对照一致；verify.sh 全绿。

## 9. 风险与暂停令约束

- **暂停令（硬约束）**：本包消费面总表 162（通知分级矩阵）/163（Live Activities）正处用户暂停令下。影响定界：本包**只补服务端生产者**，条目进的是现行已在役的通知流通用面；不解冻 162/163、不做分级呈现、不做锁屏在场感、App 零改动。App 分类器对 fail 信号 kind 的归类是 1.7.0 时代已在役行为，非本包新增消费。162/163 解冻时，本包条目自动纳入其分级/在场范围，无需再动服务端。
- **刷屏风险**：cron 同因失败高频重复——已由 incidents 聚合＋基线双闸处置；kanban 重试风暴同理由 task_run 终局失败才产条目（中间重试不产，施工时以 task_runs 终态为准、勿用 task_events 逐事件产条目）。
- **泄密风险**：error 字段含命令 stderr/路径/额度信息——条目只许一行截断摘要（拟 ≤120 字、去路径与堆栈），细则施工时钉进自测断言。
- **读时成本**：/notifications 每次读多两处 SQLite ro 查询——executions/incidents 量级为十级、kanban 单板，成本可忽略；LIMIT 与基线过滤必须带上，不许全表扫历史 executions（其行数随时间增长，查询须走 finished_at/基线下界）。
- **双生副本风险**：overview 已入关（网关为正本），companion 侧旧 overview_bridge 若仍在役须在施工时确认其不重复产条目（批三后通知面以网关为准，施工前复核一次，**此点本方案未查实**）。
