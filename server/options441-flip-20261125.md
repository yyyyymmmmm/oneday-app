## 行为验证（真实请求，非仅配置回读）

方法：经 8642 `POST /v1/runs` 发最小真实请求（自建会话），指示模型就一个二选一问题调用 present_options 工具，共三轮：

- 第 1 轮（run_b51db656，会话 options-flip-verify-20261125）：模型未调用工具、直接文字作答——模型裁量未触发，不作判据。
- 第 2 轮（run_3369ebe3，会话 options-flip-verify2-20261125）：**模型调用 present_options**（消息行 6511 tool_calls 实证，入参两选项「全量备份／增量备份」），**handler 返回 `{"success": true, "noted": true}`**（行 6512）——证明闸开后工具已进 api_server 工具面、platform 与闸门双复查通过、pending 登记成功。终态助手行 6513 已落库。
- 第 3 轮（run_f37fdc18，会话 options-flip-verify3-20261125）：同型复现，另以 0.4 秒粒度旁路轮询 state.db 全程盯会话行变化。

**缺陷实证**：第 2、3 轮终态助手行的 `display_metadata` 均为 None——pending 已登记，`_attach_options` 却未把 options 写进任何一行；第 3 轮全程轮询中 options 标记从未出现（非「写后被覆盖」）。

**根因定位（证据链）**：

- 机器本体无误：在容器内以与真实 run 相同的会话变量绑定（session_key＝run_id、session_id＝会话 id）调 handler 登记、再调部署本体的 `_attach_options`，两种行形（单助手行／与真实轮同构的五类行）均成功落卡（display_metadata.options 写入实证，试验行已清理）。
- attach 守卫链中唯一与「真实流量时序」相关的环节：`latest_message_row_id(..., require_text=True)` 要求目标助手行在 _finish 执行时**已提交入库且 active=1、正文非空**。第 3 轮轮询显示终态助手行与 session_meta 行在同一瞬间（≈3.2s）才出现——终态行由轮次收尾的交付提交才落库，而 `_attach_options` 挂在 `_finish` 发布终态**之前**，此刻库里只有正文为空的 tool-call 助手行（被 require_text 跳过），查无可落之行 → 静默无卡（该函数全守卫 fail-closed、无日志）。
- 与自反应 attach 的差异：反应 attach 落在**用户行**（轮开始即在库），不受此时序影响；§441 attach 落在**助手终态行**，是全仓唯一受交付提交时序影响的 attach。
- 注：时序因果系上述证据下的最强解释（轮询粒度 0.4s 内未能把「行落库」与「_finish 执行」再分先后）；修复方向不受此不确定性影响（见下）。

**修复方向（待主线裁，走新版部署包）**：attach 落点后移到终态行交付提交之后（如在 delivery row 落库后补挂），或 _attach_options 在查无文本行时对本 run 的 pending 做一次短延迟重试；改后须以真实 /v1/runs 请求复验落卡，不得只凭 Part A/B 自测关账——本次正是自测全过而真实流量不落卡。
