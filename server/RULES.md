# 部署包规矩（RULES）

2026-11-22 用户亲裁立规：Hermes 本体功能不许只活在单台部署的私有补丁里——其他用户部署必须功能完整。此后服务端改动一律走本包。

## 1. 先入包，后应用（铁序）

1. 任何服务端行为改动（补丁、端点、companion 配置契约）先落本包：改 `patches/` 或 `services/`、更新 `manifest.yaml`（含 sha256）、在 `CAPABILITIES.md` 登记或转正对应能力与探针。
2. 包版本号递增（见 §2）后，才许用 `install.sh` 从包应用到某个 instance；**禁止直接在服务器上改补丁文件**（急修也要先回包再应用，事后补票视为违规）。
3. 应用后必跑 `verify.sh`，结果留档；「宿主文件改完」不算完成，认「容器内回读哈希＋行为探针」双证据。

## 2. 版本号怎么递增（语义化）

- **patch（1.0.x）**：补丁内容修正、不增减能力（如契约修复、文案/小 bug）。
- **minor（1.x.0）**：能力增减或转正（新端点、新补丁文件、规划能力转在役）、companion 契约变化。
- **major（x.0.0）**：目标 Hermes 版本变化（target 镜像升级）、包结构或安装契约不兼容变化。
- 每次递增在 manifest.yaml 更新 version 与 released，并在报告/提交信息里写明动了哪项能力。

## 3. 与上游 Hermes 升级的关系

- 本包只对 `target.hermes_image` 声明的版本负责；install.sh 版本不符即停手，绝不把旧补丁硬敷到新上游。
- 升级流程：先在包内更新 target → 逐个补丁拿新上游原版与 `upstream_baseline_sha256` 对账、rebase 补丁差异 → CAPABILITIES 逐项跑探针 → 全齐才许应用到 instance。
- 上游原版基线（服务器 patches/*.orig）是 rebase 的锚；换基线时同步更新 manifest 的 upstream_baseline_sha256。

## 4. 补丁退役条件

某补丁承载的能力被**上游 Hermes 正式合入**、且在不挂该补丁时 verify 探针仍全齐 → 该补丁退役：从 manifest 与 patches/ 移除、CAPABILITIES 对应行改注「上游自带（YYYY-MM-DD 退役）」、minor 版本递增。退役是补丁的正常归宿，不是失败。

## 5. 红线（任何批次不豁免）

- 服务器内存 ≥80% 立即停一切操作；动手前先查。
- 凭据/token 一律不进包、不进报告；包内只留键名与占位符，真值从部署者自己的保险库取。
- 单文件 bind mount 应用必须原地改写保 inode（或改后重启＋容器内回读哈希双验）——2026-11-12 钉死教训。
- 备份命名沿惯例 `.bak-YYYYMMDD-<slug>`；回滚基线先行，验不过即回滚，不带病上线。
- 生产服务端的不可逆操作仍按主线纪律：先报方案＋回滚基线、确认后执行。

## 6. 共写与载荷纪律（2026-11-26 司礼监批立，即刻生效）

来历：2026-11-26 晚两条部署线共写同一棵在役树两次撞车——20:13 一线收尾同步以旧基线副本覆写另一线刚部署的两件文件、端点一度 404；同晚两线同抢 2.18.9 号段与同名回滚基线目录。

1. **载荷一律剥权限 644**：打包/传树（tar、scp、rsync）必须显式把文件权限剥为 644（目录 755），不许把本地工作区权限带进包——本轮曾因 tar 载荷带本地 660 权限、容器读不了 api_server.py 致网关未起听。
2. **同一棵部署树只许串行窗口落**：同一 instance 的部署树，同一时刻只许一条线部署；确需并行时，同步范围必须互斥（文件集不交叠）、且**回滚基线目录与版本号段预先划界**（各自独立目录、号段不重叠），开工前在派单/简报里写明。
3. **严禁整文件覆写他线增量**：叠版只许在当前在役树上移植自己的增量；在役实物与登记哈希为准，他线已部署件全量保留。
