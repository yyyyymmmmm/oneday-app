## 1. 施工前 4 项未查实 —— 查实结论

1. **kanban worker 失败的可靠人为触发姿势**：试定结论——**杀 worker 进程最可靠**。实测：测试看板任务的 worker（kanban_worker_client＋managed_worker 两进程）被杀后，心跳停摆约 30 秒内 reaper 即把 run 收为 status/outcome＝crashed、error 记「pid not alive [managed worker lost: EOFError]…」。反面实证：方案原拟的「无效 model_override」**不可靠**——worker 在供应商重试回路里长挂 ≥5 分钟不终态（心跳持续、consecutive_failures 不动），本次即靠杀进程才收口；坏模型任务随后被自动重试（run 3），亦同命。另实证：worker 自行 kanban_block 的任务收 outcome＝blocked，**不**算失败、本源正确不产条目。
2. **companion 旧 overview 面双产可能**：**排除**。companion 容器不存在（2.0.0 已整容器退役，docker ps 无此容器、无进程、无 8644 监听）；在役 nginx vhost 的 /api/overview-bridge/ 已改指 127.0.0.1:8642（网关进程内模块为唯一生产者，conf 里 8644 字样仅剩 2026-11-09 的历史注释行）。
3. **cron_incidents 的 error_sig 聚合口径**：读容器内 /opt/hermes/cron/incidents.py 定案——事故键＝(job_id, error_sig)，error_sig＝sha256(job_id＋归一化 error 前 200 字（时长数字掩码）)[:12]，incident id＝job_id[:6]_sig；状态机 detected→alerted→resolved/closed；error 入账前已经 agent.redact 去敏并截 500 字；同键复发只刷新 last_seen_at（resolved 复发会重开 detected）。**故本源直接读 cron_incidents 开放行（state IN detected/alerted）即为聚合后口径，不重聚合 executions**，与方案 §4.1「按 incidents 聚合产条目」一致。
4. **版本号与能力编号**：主线分配版号 **2.4.0**（现行 2.3.1 顺延）；CAPABILITIES 现行最大 #39（2.3.0 的 #38/#39），本件取 **#40**。
